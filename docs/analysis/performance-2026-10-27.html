The main-process bridge accounted for 97.5–97.9% of the first-open wait. The remaining 0.7–0.9 seconds include editor construction, layout, two animation frames and automation observation delay; this is not a precise isolated React render measurement.

Separate instrumented engine runs found fresh engine startup of 24.5–38.3 seconds. The first Word import took 2.0–10.5 seconds; repeated imports took 0.31–0.43 seconds. Describing the document for the editor took 3.0–4.8 seconds, including 1.9–3.3 seconds reading text portions and font properties. Copying the original to a working file took only 1.6–3.3 milliseconds; the returned document JSON was 67,975 bytes.

The bridge waits for the complete import, traversal and JSON response before the editor receives any document content. Traversal repeatedly enumerates paragraphs, tables and portions and retrieves six font properties separately through the synchronous Python-to-LibreOffice UNO bridge.

A temporary paired experiment batched those font reads using getPropertyValues. Median describe time was 3.72 s with separate reads and 3.41 s with batching (about 8% lower); all three pairs were faster, but the small sample does not establish a guaranteed improvement. All three outputs matched exactly. This is a modest, variable opportunity, not the main explanation for the initial delay.

The production status message says “Local document engine ready” after checking executable presence; it does not mean LibreOffice has started. That makes the first-open wait particularly unexpected.

Priorities supported by the evidence
  1. Reuse a private, versioned LibreOffice profile. Keep it under the application’s user-data directory, separate from the user’s normal LibreOffice profile. Manage single-instance/profile ownership and migration. The experiment shows about 17 seconds of avoidable initialization on this machine; first-ever initialization remains necessary.
  2. Warm the engine after the welcome window is ready. This changes when users wait and should show an accurate initialization state. It overlaps work rather than eliminating it and uses background memory.
  3. Package an audited document-engine subset. Review dictionaries, translations, help, icons, optional extensions and unused office modules. Non-English dictionary bundles alone occupy 430.0 MiB raw; help has 5,334 files despite using only 10.7 MiB. Keep the Writer/Word 97 filter, UNO/Python, needed shared libraries, fonts and all required notices. Confirm dependencies and rerun bookmark, signature-frame, formatting and binary .doc save/reopen checks. These raw totals are not guaranteed installer savings.
  4. Exclude redundant frontend node_modules from app.asar. The renderer is already bundled into about 0.70 MiB of dist assets. The archive also holds 41.4 MiB of runtime dependency files, including 23.1 MiB of Lucide files. Main/preload/engine use Electron and Node built-ins. Tighten packaged files and verify the resulting app and notices.
  5. Then optimize extraction and renderer work. Batch and cache remote property reads, measure enumeration costs, and avoid serializing the full editor document during unrelated React renders. The current full-document structural guard also scans on each edit. These are secondary to initialization for this sample.

A web installer can make the initial executable smaller but still downloads the application payload. Requiring an existing system LibreOffice could remove the bundled-engine download, at the cost of a prerequisite and version compatibility work. Changing Electron would address its 18.7% portion while leaving the larger engine and document-extraction issues.

Code evidence, method and limits
  • package.json:53 copies all of .cache/libreoffice, excluding only the MSI. Setup uses an administrative extraction of the full upstream installer.
  • electron/engine.mjs:25 creates a fresh temporary profile; close() removes it. It launches soffice and an external Python process connected by a named UNO pipe.
  • electron/main.mjs:17 starts the engine lazily on first open; :50 reports availability from executable presence.
  • engine/worker.py:92 imports the file; :104 reads portions/font properties; :148 walks tables and paragraphs; :187 builds the complete document description.
  • src/App.tsx:37 computes the full save payload on each component render. src/editor.ts:20 validates structure with full paragraph scans. These are code-level opportunities; their individual costs were not isolated.

Measurements used the v0.1.1 unpacked Windows x64 release on the development machine (Ryzen 5 5500U, 12 logical processors, ~11.9 GiB RAM). The installer itself was not rebuilt or installed. Size inventory includes negligible Python bytecode caches created by diagnostics. No cold reboot or filesystem-cache flushing was performed; initial import was visibly slower than later runs. Antivirus, signing, storage throughput and installer extraction time were not isolated. Results are local measurements, not guarantees for another computer.

Packaged app timings use the original bundled worker and production UI, with the native file dialog stubbed to the attached sample. Standalone engine stage timings use a temporary wrapper and cProfile, so some diagnostic overhead is included. Profile reuse compares one new profile against two sequential restarts with the same dedicated profile. Batching compares three alternating original/batched descriptions of the same loaded document and checks exact JSON equality.

Only diagnostic scripts and this report were added; production source and the installer bytes were not edited. Raw data: portable measurements JSON. Temporary harnesses and detailed profiler outputs remain in test-output/performance.
