What a smaller LibreOffice build would involve

First remove unnecessary language assets, dictionaries, help, galleries, templates and surplus icon themes through a tested manifest. The earlier inventory found 455 MiB of dictionary bundles and 262 MiB of translations, both unpacked. Those numbers do not predict compressed installer savings. Retain required fonts and drawing support for the signature frame.

For a source build, the pinned 26.8.1.1 configuration exposes controls for help, language selection, dictionaries, themes, Java and optional extensions. It also documents module file-list splitting, rather than a ready-made Windows “DOC-only engine” build. The official Windows recipe enables several optional features we do not use. Configure source · Windows release recipe

Keep size reduction separate from startup optimization.

Removing resources does not automatically eliminate office initialization or synchronous UNO traversal. Profile reuse and background initialization remain relevant. Electron also remains a separate payload after replacing or slimming the engine.

Fork feasibility, dependencies and practical constraints

The Word filter links against Writer, shared drawing/layout libraries, storage, text and font infrastructure and UNO. Its library also contains OOXML and RTF code. Consequently, simply copying the Word-filter DLL or removing every dependency with “draw” or “oox” in its name is unsafe. Rejecting .docx at the application boundary can remain strict even if the underlying engine contains shared support for other formats. Filter dependencies

Candidate settings include --without-help, --without-myspell-dicts, --with-galleries=no, --with-templates=no, --with-theme=colibre and --without-java, with only required UI languages. These are research candidates, not a tested configuration. The present Python/UNO adapter requires Python support. Several aggressive feature-disable switches are described upstream as unfinished, and the generic GUI-disable path is not a simple Windows headless build recipe. Build controls and checks

The current official Windows recipe merges many libraries together, which makes post-build pruning of code harder. An independently built variant can change that tradeoff. Build setup uses a native C++ toolchain; the upstream Windows baseline names Visual Studio 2022 with WSL as a helper. A fork would require rebuilding, tracking security fixes, maintaining patches and checking a document corpus on every update. Release settings · Build baseline and code structure

LibreOfficeKit offers native access to the same engine; it is not a separate lightweight parser. Its published API emphasizes conversion, rendering and editing commands. Reproducing our paragraph/font/bookmark adapter needs separate API validation. A native component performing whole-document extraction inside the engine could reduce remote UNO traffic, but this is an architectural proposal, not a measured result. LibreOfficeKit

I also found DeepSeek’s open-source dsh-libreoffice-kit, which documents reduced native builds and binary .doc conversion. Its exposed API focuses on conversion/rendering rather than live bookmark editing, and its packaging documentation describes internal release preparation. It is useful evidence and a possible source of build techniques, not a verified drop-in engine for Nebula. Packaging details

Licence implications for the existing MIT application

LibreOffice is available under MPL 2.0, with additional licences for included components. Forking and redistribution are permitted subject to those terms. When distributing a custom binary outside our organization, provide recipients access to its corresponding MPL-covered source, including modifications, and retain notices. Keep the exact source version, patches, build recipe and dependency notices with the release. LibreOffice licences · Mozilla distribution FAQ

Nebula’s independently written Electron/React code can remain MIT. The forked upstream files cannot simply be relabelled MIT; their applicable upstream terms remain. MPL obligations apply at file level, and unrelated original files can use another licence. A commercial engine likewise keeps its own terms: an MIT wrapper does not grant users rights to redistribute that engine. MPL larger works · Aspose deployment licences

Alternative-specific findings and exclusions
  • Aspose.Words: strongest commercial replacement candidate in my assessment. Documentation covers legacy DOC import/export and editing text, fonts, bookmarks, tables, fields and shapes without Office automation. Use its Node API or a local .NET helper; measure the actual redistributable package and runtime. Suitable end-user redistribution licensing is required. Features · Licence types
  • Spire.Doc: documented legacy Word editing, bookmarks and shapes. The free .NET edition limits reading/writing to 500 paragraphs and 25 tables. Our editable-body paragraph count alone does not establish eligibility: other document regions and tables also need examination. A free edition is not the same as open-source code. Edition limits · Vendor examples
  • Apache POI HWPF: useful lower-level open-source candidate, but its own documentation characterizes support as incomplete and warns edits may create invalid files. Its public bookmark interface exposes retrieval/removal, without a convenient add method; our create/rename/preserve workflow would need validation or lower-level work. A Java runtime would also need distribution. HWPF limitations · Bookmark interface
  • Word automation: would remove the bundled office engine from Nebula by using an installed copy. It shifts that requirement to the machine and retains an office process. Do not assume Word for the web or default save operations produce binary .doc; explicitly select Word 97–2003 format. Save enumeration · Installed Word prerequisite
  • ONLYOFFICE Docs: excluded as a direct solution because its documentation says legacy .doc is not available as a saving format. Saving limitations
  • Aspose.Words FOSS: despite its MIT licence, its documented open-source edition does not read or write DOC. It does not meet this project’s binary-format requirement. FOSS format exclusions
Decision and acceptance criteria

My recommendation: keep the current engine initially, implement the already measured startup improvements, and build a reproducible reduced package. Consider a custom upstream build only if packaging cannot meet the size target. Evaluate Aspose.Words alongside that work if a commercial dependency is acceptable. Reserve a deep Writer fork for a demonstrated need that neither approach can meet.

Before selecting an engine, test the original agreement and a wider representative corpus: genuine OLE .doc output; font and text edits; all 36 bookmark names/anchors including the three outside the editable body; add/rename/delete; signature label and floating frame; tables, headers, footers, fields, pagination and repeated save/reopen. Check output in Microsoft Word as well as the candidate engine. Measure fresh launch, first and repeated opens, compressed installer bytes and complete installed footprint using the same fonts and machine.

No smaller installer size or faster startup is promised for an unbuilt variant. This research did not create a fork, change application dependencies, buy licences, install trial engines or upload the agreement to a service. Sources were checked on 27 October 2026; the build-source review was pinned to the version currently bundled, 26.8.1.1.
